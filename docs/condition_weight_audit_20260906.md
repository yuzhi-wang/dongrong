# 条件与权重审计（2026-09-06）

本记录为2026-09-06当时的审计结论。检查范围包括当时的 System/User 提示词、传给模型的20个产品字段、12款产品目录中的具体规则、本地硬过滤、历史重排及18:51回测的86条成功结果。此次仅分析，不修改提示词、权重或历史报告，不调用模型。

## 结论及证据等级

当前没有“单位性质占20%、公积金占30%”这类逐字段数值配置。字段之间的相对重要性由提示词约束、模型生成名次，因此提示词中的“优先”“主要依据”“弱同分项”都是可能影响排序的隐含权重。代码中明确的混合权重是模型归一化名次50%、历史产品频率50%。

需要区分三类发现：

- **已存在的排序规则**：申请区间完整覆盖优先、利率先上限后下限、无目标期限时偏向更长期限、历史频率权重0.5。这些是实现中的实际决策，不等于已经证明合理或错误。
- **已观察到的解释错误**：公积金缴存基数被当成月缴额、未知房产所在地被当成本地、缺少最高利率仍声称利率区间较优。可能影响排序，但没有原始完整推理，不能仅凭理由确认具体名次变化的因果。
- **需要补强的约束**：超过门槛后继续加分、条件放宽再重复加分、同一事实的多个字段重复计分、未被产品使用的个人信息参与排名。不能将这些全部说成已经发生的代码错误。

## 全部条件分类检查

| 条件组 | 当前情况 / 风险 | 应遵循的判断方式 |
| --- | --- | --- |
| 工资、收入金额、支付方式、个税、代发银行 | v4.1 已纠正本行代发的通用优先；其余字段仍可能被拆成多项奖励 | 分别核对产品明确的金额、方式、银行和连续月数条件。它们可以是不同的必需条件，但不因此成为多个无条件加分项。同一工资数据的金额和区间表示只算一份事实 |
| 公积金是否有、基数、月数、月缴额 | 存在字段含义混用的真实例子；“有公积金”不能再作为已满足缴存条件以外的普遍奖励 | 基数不等于月缴额，未知缴存比例不能换算；各条件按同一客群路径核对。超过最低基数后，不默认随数值持续加分；只有目录明确分档或优惠时才能应用 |
| 社保月数、基数、连续性 | 可能把“有社保、缴存久、未断缴”重复当成综合客户质量；现有提示词没有逐项门槛饱和规则 | 按产品要求确认月数和连续性。不能把收入或公积金基数替代社保基数。都已满足同一门槛时，不自设年限越长越优 |
| 在职年限、工作稳定性 | “3年以上远超6个月”可陈述事实，但不自动构成比其他满足条件客户更强的产品匹配 | 达到门槛即可；不得同时按在职长、工资稳定、社保稳定重复奖励同一事实。目录明确12个月更优等规则，只能作用于对应产品路径 |
| 单位性质、优质单位、白名单 | 目录同时存在准入类别、缩短缴存要求、辅助偏好三种用途 | 按具体用途执行；不能在使用优质单位放宽门槛后，再无依据增加“单位好”的通用分。单位类别不等于已进白名单，某银行的优质单位定义不能直接搬到另一产品 |
| 学历、年龄、身份、婚姻 | 部分产品用学历和年龄确定门槛；未发现独立数值加分配置 | 仅解释产品实际引用的条件。研究生可能使某路径在职要求缩短，不代表对所有产品加分。个人法律身份不等于工薪身份；婚姻等未被产品使用的信息不应影响名次 |
| 房、车、套数、面积、按揭、结清状态 | 资产属性容易变成多次奖励；“本地有房”误判已有实例 | 用于对应资产路径、抵押要求或明确辅助项。是否有房、套数、面积是同一资产的不同属性，按实际规则核对；没有数量或面积门槛时不因更多、更大而加分 |
| 本行房贷、车贷、理财、存款、信用卡关系 | 与工资银行相似，不能把关系本身设为通用优势 | 必须有产品对应路径且客户字段能证实该关系；账户总数不证明银行归属、活跃状态、余额或正常还款期限 |
| 经营身份、流水、营业执照、经营收入 | 当前缺失较多，产品目录可能包含相应路径 | 经营性还款来源、普通企业单位性质不能替代企业主身份或实际流水；流水越大也不能自动改善与不使用流水的路径的匹配 |
| 申请额度、区间、产品最高额度 | **明确存在“覆盖整个区间优于部分覆盖”策略**。59位客户选择额度优先，可能影响较多客户 | 精确申请额、可接受范围、问卷金额档位应区分。比如“11–30万”并不必然意味着一定需要30万。当前全部按上限覆盖比较是保守策略，不应解释为已确认的客户硬需求。多个产品都覆盖时不再按上限大小加分 |
| 年利率、利率范围 | **明确采用先比较上限再比较下限**，属于偏保守的排序策略；还存在只有下限便声称区间较优的输出 | 公开利率区间不是客户实际报价。区间交叉时不能断言谁一定便宜；未说明偏好最低可能成本还是成本上界时，不应将固定上限优先视为客观最优。缺失上限不奖励，也不自动惩罚 |
| 期限 | **未提供目标期限时，更长最长期限仍获弱同分优势** | 缺少目标时，应待确认；并非人人都希望期限越长越好。能覆盖明确目标才提供需求匹配证据；不要同时按长期限和未经计算的低月供重复加分 |
| 放款速度、资金紧急程度 | 已有规则禁止凭空推断时效，未发现固定速度加分实现 | 紧急程度只表达需求。产品没有明确时效时，不能据银行类型、利率、是否有资产猜测速度 |
| 还款方式、来源、用途 | 排序规则第3条要求继续比较，但没有明确偏好时容易由模型自行定义“更优” | 只有明确需求与产品支持情况才能比较。薪资还款来源不是一份额外工资证据；不能默认先息后本或某种还款方式更适合所有客户 |
| 年龄、地区、逾期、查询、负债、机构数等硬规则 | 硬过滤执行排除，`passed_rule_count` 未传给模型且未进入重排，没有累计通过数加分 | 保持门槛与排名区分；通过更多硬规则不等于更匹配。年龄或房产所在地若被具体客群路径再次使用，应仅核对那条路径条件，不构造通用优质客户分 |
| 产品名、银行名、产品类型、是否优先推荐 | 产品名和银行名用于识别；`是否优先推荐` 字段未传给模型 | 不按知名度或名气加分。产品类型用于对应需求。不能从名称推断利率、审批难度或速度 |
| 产品备注、可辅助、优先、放宽、加白 | 备注会传入模型，混合了实际条件、辅助描述及需要核实的例外流程 | “可考虑加白”不等于已白名单；“可辅助”只作用于主要条件相近的比较；门槛放宽用于确认适用条件，不再重复作通用加分。与硬过滤有关的例外不应由模型擅自恢复排除产品 |
| 信息完整度、路径数量、同一事实的多个字段 | 已禁止按路径数量和条件条数累计加分，但“针对性更强”仍留有主观解释空间 | 对同一条件的精确值、区间值、布尔值去重并核对一致性；不同产品需要的条件不同，不能仅比较资料填写数量。选择最强独立路径，但不将其他已确认事实全部忽略 |

## 已观察到的具体例子

1. **C071 / 邮享贷**：客户 `provident_fund_base=31188`，模型却写“月缴额远超2400元”。产品条件是“连续缴存24个月及以上（或月缴额>2400元）”。基数与月缴额不同，不能据此前者确认后者。这是明确的数据含义错误。
2. **C216 / 诚易贷**：客户城市未知、有按揭房，模型认定满足“本地有房”放宽条件，并重复在两条理由中引用该优势。房产所在地未被确认；两次引用本身不能证明内部重复计分，但暴露了同一事实重复强化的风险。
3. **C150 / 中银e贷**：产品最高年利率为空，模型根据最低年利率3.1%声称“利率区间较优”。不能由下限推出整个区间或客户最终成本较优。

## 建议的统一修订原则

先给每个产品条件确定用途，再决定能否影响排序：

1. **路径必要条件**：核对是否满足；不能凭条件数量设总分。
2. **同一条件的补充属性**：用于核对或消除不确定性，不另立奖励。
3. **产品明确的门槛放宽**：应用实际门槛，避免再加一遍优惠分。
4. **产品明确的辅助偏好**：主要条件相近时使用，不能压过必要条件。
5. **客户明确需求**：比较产品是否覆盖需求；不要替客户补出上限、期限或风险偏好。
6. **未被产品或客户需求使用的事实**：不参与排名。

优先处理明确的数据含义错误、重复事实和无目标期限的默认奖励；额度区间和利率上限优先应标注为待验证的业务策略，不能无依据换成另一套固定偏好。历史权重需与提示词改动分别验证。当前本轮未再修改运行配置。
